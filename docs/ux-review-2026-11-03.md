# UX review — songbook, full surface (web + TUI)

Reviewer: UX expert advisor. Date: 2026-11-03.
Ground truth: the four screenshots pasted in this conversation (metadata ×2,
triage ×2), plus the code listed in the task. Everything below is either
observed in a screenshot or cited to a file/line in code; anything I could not
verify on either is marked *speculation*. Screenshots were low-resolution, so
where code and pixels agree I cite both; where I rely on code alone I say so.

---

## How the surfaces scored, in one paragraph

The shared design system is genuinely good: the marker/label split (`· ? × ✎ ✓`
say what needs attention; lowercase labels say what a line is; muted
`(was: …)` provenance only on disagreement) is implemented faithfully on both
surfaces and shows up correctly in the triage screenshots (e.g. the row that
reads `lyric … (was: …)` after pressing `l`). Keyboard operability, live
regions, `aria-keyshortcuts`, and no-color-only-meaning are all present in the
web code, not just claimed. The weaknesses are concentrated in three places:
(a) **focus ownership** on the web triage screen, (b) **TUI mode feedback**
(edit mode and quit have no guard rails), and (c) **small consistency drift**
between the two surfaces the brief explicitly asks to keep unified.

---

## Findings (prioritized)

### F1 — TUI: quitting destroys all triage work with one keystroke, unconfirmed
**P1 · effort M · surface: TUI, all phases**

`Esc` and `q` in triage (and metadata) map straight to `Phase::Quit`
(`src/tui/mod.rs:149`, `src/tui/triage.rs` `handle_triage`: `Key::Quit |
Key::Escape => self.phase = Phase::Quit`); Ctrl+C too. There is no
confirmation; the only feedback is printed *after* the TUI has closed
(`src/main.rs:132`: "Triage cancelled; no output written."). Every keep/
discard/lyric decision is gone. The web surface guards the identical action
with a `window.confirm` whose copy names exactly what is lost
(`web/app.js:961-965`). The power surface is the *less* protected one — an
Esc reflex (habitual from the web preview, where Esc = back) costs the whole
session.

Suggestion: a two-step quit — first Esc/q prints a centered confirm line
("Quit? All triage decisions will be lost — press q again to quit, any other
key to continue"), matching the web's confirm copy. Ctrl+C can keep its
immediate semantics (that convention is understood), though the same confirm
would cost nothing.

### F2 — Web: every triage action yanks keyboard focus back into the line list
**P1 · effort S · surface: web, triage screen**

`renderTriageList` ends with an unconditional focus pull
(`web/app.js:303-308`): unless the current row's button already has focus, it
calls `.focus()` on it after *every* render, i.e. after every verdict, undo,
or navigation. Consequences observed in code:

- A keyboard user who Tabs from the list into the actions group and presses
  Enter on "Discard" is thrown back into the list, and must re-Tab past
  Keep/Discard/Lyric/Chord/Header/Noise/Edit/Undo/Next flag/Previous
  flag/Accept/Preview to reach the next action — roughly a dozen stops per
  decision.
- A screen-reader user navigating by buttons gets their reading position
  reset on every action.
- Mouse users are unaffected functionally, but the click also moves focus
  (visible as the orange ring jumping rows in the pasted triage screenshots).

This is the one place where the app's otherwise-strong keyboard story
contradicts itself: letters are global, but button focus is not stable.
Note the trade-off honestly: the focus move is what makes a screen reader
announce the *next* current line after a verdict. Keep that feedback, lose
the theft.

Suggestion: only steal focus if focus was inside the triage list before the
action (or if the pointer was used); when focus is in the actions group, keep
it there and announce the new current line through `#triage-live` instead
(e.g. "Line 12, chord-only, pending: <text>"). Effort S–M.

### F3 — TUI: edit mode keeps the normal-triage key legend on screen
**P2 · effort S · surface: TUI, triage/edit**

While `state.editing` is true, every letter key types into the line
(`handle_triage` editing branch), but `draw_footer` still renders the triage
legend — "j/k line · f/F flag … d drop · l lyric …" (`src/tui/triage.rs:226-244`,
phase-keyed only, not editing-aware). A user in edit mode reading the footer
will press `d` expecting to drop and will instead insert the letter "d" into
the song. The only mode cue is "Editing: …█" in the Selected-line panel.

Suggestion: an editing legend ("type to edit · Backspace delete · Enter save ·
Esc cancel"), same three-line footer slot. Effort S.

### F4 — TUI: line editing is append/backspace-only
**P2 · effort L · surface: TUI, edit mode**

The edit buffer only supports `Char` push and `Backspace` pop
(`handle_triage`); there is no cursor movement, no insert-in-middle, no
delete-word. Fixing a typo in the middle of a long lyric line means
backspacing to it and retyping the tail. The web's inline `<input>` allows
full cursor editing — so the two surfaces have materially different editing
capabilities, and the TUI (the power surface) has the weaker one. This is a
real capability gap, not just polish; effort is L because it implies a real
cursor model in the TUI. If it is judged out of scope, at minimum document
the limitation in the edit legend ("append-only") so users don't hunt for a
cursor.

### F5 — Web: "(inferred)" renders *before* the field, not after it
**P2 · effort S · surface: web, metadata screen**

In `renderMetadata` (`web/app.js`), the inferred hint span is appended to the
field wrapper *before* the label: `wrap.append(hint)` then
`wrap.append(label)` — so `(inferred)` appears above/left of the label in the
flex row, instead of trailing the field the way the TUI does
(`{label} {value} (inferred)`, `src/tui/triage.rs:36-42`) and the way the
screen's own copy promises ("Fields marked 'inferred'" — marked *after* the
fact reads naturally). Code is deterministic here; the pasted screenshots are
too small for me to confirm the exact visual position, so I flag placement on
code evidence.

Suggestion: append the hint after the label (or after the input inside the
label), so it reads "Title [input] (inferred)". Effort S.

### F6 — Web: Tab inside the inline line editor *commits* the edit
**P2 · effort S · surface: web, triage edit input**

The inline editor's keydown handler maps `Tab` to `confirm`
(`web/app.js:349-352`) alongside Enter, and Escape to cancel. Tab is the
canonical "leave this control" key; a keyboard or screen-reader user who
tabs out of the editor to check the action buttons silently *saves* a
half-typed edit. The TUI ignores Tab in edit mode — the surfaces disagree on
the same gesture.

Suggestion: remove the Tab branch (Enter saves, Esc cancels, Tab behaves
natively). If tabbing away should save, do it on `blur` explicitly and
announce it. Effort S.

### F7 — Paste-only books are impossible (scope question — for the facilitator)
**P2 · effort M · surface: web, load screen**

Book mode is reachable only by choosing/dropping ≥2 files
(`file-input`/`drop` handlers, `web/app.js:1128-1147`). The load screen's
paste box always creates a single song, and pasted songs can be *added* to an
existing book only from the book-details and book-export screens — which you
cannot reach without files. The stated primary users are non-technical
collaborators copying from tab websites; for them, "several pasted songs →
one book" is unreachable. The brief describes books as "mixed file/pasted
sources", which may mean paste-only books are out of scope by decision — I am
flagging the question, not answering it. **Flagged for the facilitator:** is a
paste-only book (e.g. a "Make this a book" toggle next to the paste box, or
two paste slots on the load screen) in scope?

### F8 — Web book mode: "Back to book details" throws away your place
**P2 · effort M · surface: web, book flow**

`showBookForm` resets `book.current = -1` (`web/app.js:571-583`, with the
comment that Start triage resumes "at the first song"). So in a 10-song book,
going back from song 9 to fix the book title, then pressing "Start triage",
lands you on song 1's screen; sessions are remembered, but you must press
"Next song" through every completed song to climb back. The progress banner
("Song N of M") is good; the resume behavior undercuts it.

Suggestion: remember the last unfinished song index and resume there (the
"first unfinished" rule is already implicitly used by `bookForward` skipping
errored entries); alternatively give the book-details screen a per-song
status list ("✓ done / ▸ current / · pending") with jump links. Effort M.

### F9 — Vocabulary drift between web and TUI (and within the TUI legend)
**P3 · effort S**

The brief mandates one vocabulary; drift spotted in code:

- TUI footer: "d **drop**" (`tui/triage.rs:235`) vs web button "**Discard**"
  and label "discarded".
- TUI footer: "a **accept rest**" vs web "**Accept remaining pending**".
- TUI panel titles "Input review" / "Input · N lines…" vs web heading
  "Review each line".
- Web preview `aria-keyshortcuts` says "s p" but the hint line and button
  only advertise `s` (`index.html:126`; `app.js:1090` accepts both).

None of these will confuse a user of one surface alone; they matter because
the owner uses both. Suggestion: align the TUI footer strings to the web
button labels (Discard, Accept remaining) or vice versa — pick one set — and
add `p` to the web hint or drop it from `aria-keyshortcuts`.

### F10 — Transpose affordance asymmetry: TUI triage, web preview-only
**P3 · effort S**

The TUI accepts `+ / − / 0` during triage itself (footer legend,
`tui/mod.rs:151-153`); on the web those keys are deliberately inert in the
triage phase (`app.js:1091-1106`) and the transpose buttons exist only on the
preview screen. A web user who realizes mid-triage "this needs to be in a
different key" must first go to preview, transpose, and come back — or do it
after. Consistent behavior would be either web triage transpose controls
(small, near the status bar) or a hint "transpose on the preview screen".
Effort S either way.

### F11 — Web screen-reader status chatter: the whole status string re-announces
**P3 · effort M**

`#triage-status` is a polite live region whose text ends in "line N current"
(`statusText`, `app.js:77-81`; `index.html:105`). Every navigation or verdict
changes that string, so a screen reader re-announces the entire "53 lines · 1
flagged · 1 pending · line 12 current" for a one-line change — while the
dedicated `#triage-live` region stays mostly silent (it only carries explicit
messages like "Undone."). The information is right, the *granularity* is
wrong: the change is one count or one line number, buried at the end of a
long string.

Suggestion: keep `#triage-status` visual but make the *live* announcement
short and about the change ("Line 12, chord-only" / "1 pending left"), via
`#triage-live`. Also note `statusText` is currently assigned twice per render
(`renderTriage` and `renderTriageList`) — harmless, but a sign the two paths
should merge. Effort M.

### F12 — Web preview container has no role for assistive tech
**P3 · effort S**

`#preview-content` is a `div` with `tabindex="0"` and an aria-label
("Song structure preview, scrollable") but no role (`index.html:138`). A
screen reader lands on it as an unnamed-ish generic focusable; it can read
the rows as plain text, but the structure (sections, metadata rows, chord
lines — which the CSS styles distinctly) isn't conveyed. Suggestion:
`role="region"` with the existing label at minimum; structuring metadata
rows/section headers as headings would be a bigger, optional win. Effort S.

### F13 — Dropping a folder (or zero files) on the drop zone is a silent no-op
**P3 · effort S**

The drop handler acts only on `files.length >= 1` real files
(`app.js:1143-1147`); dropping a directory (common: users drop their whole
"tabs" folder) yields zero entries in `dataTransfer.files` and nothing
happens — no error, no hint. Suggestion: message in `#file-error` ("That
doesn't look like a .txt/.crd file — choose files, not folders"). Effort S.

### F14 — Single-song flow has no "finished" moment
**P3 · effort S**

After download, the only exits are Back and **Start over** — a
destructively-framed button sitting right next to the export actions (visible
in the triage screenshots' third action row; also on preview). The natural
next sentence in a user's head is "convert another song." Suggestion: relabel
the post-download affordance (e.g. a "Convert another song" button that still
confirms) or move "Start over" out of the export action row. Effort S.

### F15 — TUI legend renders "· · preamble" (double dot)
**P3 · effort S (trivial)**

The triage panel title legend ends `… ✓ kept · × dropped · · preamble{…}`
(`tui/triage.rs:125`): the separator dot collides with the preamble marker
itself is a dot. Reads as one stray "· ·". Suggestion: reword ("· preamble"
→ "dot = preamble" or reorder so a dot-marker legend item isn't preceded by
another separator), same for the plain "·" case. Pure string fix.

## Things that are working well (keep / protect)

- **The label/marker channel system is implemented as briefed, on both
  surfaces.** Verified in code (`effective_label`, `wasSuffix`,
  `triage.rs:161-179`) and visible in the screenshots: after pressing `l`,
  the row label changes to `lyric` with the muted `(was: …)` suffix, and the
  pending row keeps the parser's guess with no fake provenance.
- **Honest "dropped" labeling** for kept blank/noise lines (`model.rs:176-192`,
  `triage.rs:216-247`) — the UI refuses to claim a kept-noise line "exports".
- **Keyboard-hint chips** (`<kbd>` aria-hidden + spoken "(shortcut …)" +
  `aria-keyshortcuts`) on every web button: discoverable for sighted users,
  correctly named for screen readers. This is craft.
- **Undo is stronger than advertised** — Ctrl+Z/Cmd+Z works on web
  (`app.js:1044-1050`) though the hint line doesn't mention it; either
  advertise it or leave as a bonus.
- **Metadata Enter-to-continue** (`app.js:137-142` and the book title/author
  fields) — small, correct flow accelerator.
- **Dragover state, dark mode, reduced-motion, CSP, skip link** — all present
  and unobtrusive (`styles.css`).
- **Dynamic back/next labels in book mode** ("Back to previous song", "Next
  song", "Continue to book export") — the labels do the IA work instead of
  generic "Back"/"Next". Good.
- **Failure reporting in book mode** is exemplary: failed sources are named,
  explained, excluded, and re-listed at export ("N songs ready · M skipped")
  — never silent (`loadBookSong`, `showBookExport`).

## Quick wins (small effort, visible payoff)

1. **F5** — move the `(inferred)` hint after the label. One-line DOM-order fix.
2. **F6** — remove the Tab-commits-edit branch in the inline editor.
3. **F15** — fix the `· · preamble` legend string in the TUI title.
4. **F9** — align "drop/accept rest" strings with the web's "Discard /
   Accept remaining pending"; add or remove the `p` shortcut mention.
5. **F13** — error message for folder/empty drops.
6. **F14** — relabel or relocate "Start over" next to the export actions.
7. **F2 (partial)** — even without redesigning focus flow, making the focus
   pull conditional on "focus was already in the list" is a ~5-line change
   that stops the button-flow yank.

## Structural items

1. **F1** — TUI quit confirmation (M): a confirm state in `TriageState`.
2. **F2 (full)** — a coherent focus-management model for the triage screen:
   decide once whether focus follows the pointer, the keyboard, or the
   session cursor, and document it (M).
3. **F3+F4** — TUI edit mode: legend switching is S, a real cursor model is
   L; decide together whether the TUI editor gets upgraded or gets an
   honest "append-only" label.
4. **F7** — paste-only books: facilitator decision first, then likely a
   load-screen redesign (M).
5. **F8** — book resume semantics (M): "first unfinished song" rule plus
   optional per-song status list on the book-details screen.
6. **F11** — announcement architecture: short, change-focused live-region
   messages; status bar stays visual (M).
